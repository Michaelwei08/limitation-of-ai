# AGENTS.md

Project-level guidance for Codex CLI.

This repo studies **task-scoped permission boundaries for consumer AI agents**.

Working project name:

**Personal Agent Permission Firewall (PAPF)**

Possible benchmark name:

**NonExpert-AgentPermBench**

---

## Project goal

Build and evaluate a task-scoped permission framework for consumer AI agents.

Main research question:

> Can we build a user-comprehensible, enforceable permission boundary that protects non-technical users from unnecessary personal-data exposure while preserving task success?

The project should produce measurable research contributions, not a broad AI ethics essay.

---

## Core thesis

Do not rely on the LLM itself to decide or enforce permissions.

The LLM may help with:

- interpreting user intent
- proposing candidate capabilities
- explaining permissions
- recovering from denied actions

But final permission enforcement must happen outside the LLM through:

- explicit capabilities
- scoped data access
- policy checks
- audit logs
- runtime enforcement

---

## Non-goals

Avoid turning the project into:

- a generic AI ethics essay
- a pure CoT/explainability project
- a prompt-only safety solution
- a paper claiming that LLMs can self-regulate permissions
- a UI-only permission redesign without enforceable backend logic

Do not claim that chain-of-thought is a reliable permission or explanation mechanism.

---

## Research direction

The default system design is:

1. **Task intent analysis**  
   Convert the user task into structured intent and required data categories.

2. **Capability compiler**  
   Translate intent into narrow, machine-checkable capabilities.

3. **Runtime policy enforcement**  
   Check every tool call against the scoped policy.

4. **Risk-adaptive consent**  
   Use different consent levels instead of asking users to approve every action.

5. **Audit and traceability**  
   Record what the agent accessed, what was blocked, and why.

---

## Benchmark direction

If building a benchmark, focus on realistic consumer-agent tasks involving:

- email
- calendar
- contacts
- files
- browser
- travel booking
- payments
- messaging
- cloud/device management

Each task should specify:

- user-visible task
- necessary data
- unnecessary data
- dangerous data
- allowed tool calls
- forbidden tool calls
- possible prompt-injection or exfiltration attacks
- expected policy outcome

---

## Core metrics

Use these metrics by default:

- task success
- necessary access rate
- over-access rate
- exfiltration rate
- consent burden
- non-expert comprehension score
- false allow
- false deny
- recovery quality
- auditability

Do not evaluate only task success. The project is about the tradeoff between task completion and scoped privacy/security.

---

## Research integrity

- Do not invent citations, paper claims, benchmark results, or statistics.
- Mark unverified claims as `UNCONFIRMED`.
- Distinguish clearly between:
  - established prior work
  - hypothesis
  - proposed method
  - implementation result
  - speculation
- Every factual claim in paper drafts should eventually have a citation.
- Do not report experimental numbers unless generated by code or clearly labeled as illustrative.

---

## Data and privacy

Prefer synthetic data.

Do not use real personal emails, calendars, contacts, payment records, private files, or credentials unless explicitly authorized and ethically appropriate.

Never commit:

- secrets
- API keys
- tokens
- cookies
- real personal data
- raw user-study data

Redact sensitive information in examples, logs, and outputs.

---

## Coding rules

- Build modular first.
- Avoid code files longer than 300 lines.
- If a file approaches 300 lines, split it into smaller modules.
- Keep public entrypoints stable.
- Use clear, testable functions.
- Prefer type hints where practical.
- Avoid global mutable state.
- Do not add silent fallbacks.
- If required input is missing or malformed, fail clearly.
- Do not leave empty `try`/`except` blocks.
- Do not swallow exceptions without useful diagnostics.

Keep these concerns separate:

- intent parsing
- capability compilation
- policy enforcement
- audit logging
- benchmark definitions
- metric computation
- paper/figure generation

## Testing expectations

For code changes, run targeted tests first.

Prefer:

```bash
uv run pytest
```

For benchmark changes, verify:

* tasks load correctly
* labels are valid
* allowed/forbidden actions are consistent
* metrics are deterministic
* synthetic data contains no real personal information

For paper changes, verify:

* citations are real
* claims are source-backed
* figures/tables match generated results
* terminology is consistent
